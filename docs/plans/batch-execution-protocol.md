# 批次执行协议

## 用途

本文档定义补测试和沉淀 raw reference 时的固定执行流程。

执行模型如果忘记当前应该做什么，必须重新阅读本文档，然后从“当前批次状态”继续。

## 核心原则

- 一次只执行一个小批次。
- 每批必须先明确范围，再动手。
- 每批必须测试和记录 raw reference。
- 每批完成后必须停下来汇报。
- 使用者明确说“继续”后，才能进入下一批。

## 单批次范围上限

任一条件达到上限，就必须结束当前批次：

- 最多 1 个源码文件。
- 最多 5 个强相关公开函数。
- 最多 20 个新增或修改测试用例。

如果一个文件导出很多函数，必须拆成多个批次。

## 批次开始前

开始动手前，执行模型必须先输出批次计划。

批次计划格式：

```md
本批次计划：

- 源码文件：
- 相关测试文件：
- raw reference 文件：
- 本批次函数：
- 准备补的测试点：
- 可能风险：
```

如果使用者要求“先报批次再执行”，输出计划后必须等待确认。

如果使用者要求“直接执行第一批”，输出计划后可以继续执行，但仍然只能执行这一批。

## 批次执行中

执行顺序固定如下：

1. 阅读源码文件。
2. 阅读相邻测试文件。
3. 判断当前批次函数的公开行为。
4. 编写或补充测试。
5. 如有必要，顺手修正当前批次附近明显不合规范的说明性注释。
6. 运行相关测试。
7. 更新 `docs/reference-raw/*.md`。
8. 如果有语义不清、注释冲突、疑似 bug，记录到 `docs/reference-raw/unresolved-questions.md`。

执行中不允许：

- 扩大到无关文件。
- 连续开启下一批。
- 大规模重写源码注释。
- 修改公开 API 语义。
- 为了让测试通过而改源码行为。

## raw reference 更新要求

每个批次至少要更新一个 raw reference 文件。

如果该批次只发现问题、没有足够信息形成函数记录，也必须更新 `docs/reference-raw/unresolved-questions.md`。

raw reference 必须记录：

- 源码链接。
- 测试链接。
- 轻量形状。
- 当前行为。
- 参数语义。
- 返回值。
- 边界行为。
- 测试覆盖。
- 待确认问题。

模板见 [`docs/reference-raw/README.md`](../reference-raw/README.md)。

## 批次测试要求

每批结束前至少运行相关测试文件。

推荐：

```bash
bun test src/path/to/file.test.ts
```

如果测试涉及类型、重载、导出或泛型推导，还要运行：

```bash
bun run type-check
```

如果改动影响导出或构建结果，还要运行：

```bash
bun run build
```

如果命令失败：

- 先判断是否是本批次测试写错。
- 如果能在测试范围内修正，就修正后重跑。
- 如果涉及源码语义、公开 API 或疑似 bug，记录到 unresolved 文档，不自行决定。

## 批次结束汇报

每批完成后必须停止，并用下面格式汇报：

```md
本批次完成：

- 源码文件：
- 测试文件：
- raw reference 文件：
- 覆盖函数：
- 新增/修改测试点：

验证：

- 运行命令：
- 结果：

发现的问题：

- 已记录到 unresolved：
- 需要强模型判断：

下一批建议：

- 建议文件：
- 建议原因：

状态：

- 本批次已结束，等待你确认是否继续。
```

汇报后不能继续改文件，除非使用者明确说“继续”或给出新的任务。

## 使用者说“继续”后

使用者确认继续后，执行模型才能选择下一批。

下一批开始时仍然必须重新输出批次计划。

不要因为上一批顺利，就跳过批次计划、测试或 raw reference。

## 中断后恢复

如果对话中断、模型切换或上下文压缩，恢复时按以下顺序做：

1. 阅读本文档。
2. 阅读 `docs/guides/how-to-write-test.md`。
3. 阅读 `docs/plans/codex-spark-test-and-raw-reference-guide.md`。
4. 查看 `git status --short`。
5. 查看最近修改的测试和 raw reference。
6. 判断上一批是否已经完成汇报。

如果上一批没有完成验证或汇报，先完成上一批，不要开启新批次。

## 语言规范提醒

- 中文负责描述。
- 英文负责结构。
- 测试描述、注释、文档、日志使用简体中文。
- 变量名、函数名、类型名、import/export 使用英文。
- 历史英文描述不能作为新规范。
