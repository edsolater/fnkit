# Codex Spark 测试执行指南

## 适用模型

本文档面向较轻量的执行模型，例如 `5.3 Codex Spark`。

执行模型的职责是按清晰规则推进测试，不负责做大范围架构判断。

## 当前阶段目标

当前阶段只做两件事：

1. 补齐公开 API 的单元测试。
2. 在写测试时顺手发现源码 JSDoc/TSDoc 缺口，但默认只在汇报中说明。

不要在这个阶段大规模重写 `reference.md`。`reference.md` 是后续从测试和源码说明中再提炼出来的最终索引。

执行前必须阅读并遵守 [`batch-execution-protocol.md`](./batch-execution-protocol.md)。该协议定义每个批次如何开始、如何执行、如何验证、如何汇报，以及何时必须停下来等待使用者确认。

## 执行顺序

每次只选择一个小批次，优先级如下：

1. 已有测试但覆盖不足的文件。
2. 没有测试但行为直观的公开运行时文件。
3. 核心高频工具：collection、numberish、timeTools、objectUtils、functionManagers。
4. 行为复杂或语义不清的文件。

每个批次建议控制在：

- 1 个源文件；或
- 同一文件内 2 到 5 个强相关函数；或
- 一个已有测试文件的补充。

## 单批次工作流

详细批次协议以 [`batch-execution-protocol.md`](./batch-execution-protocol.md) 为准。

1. 阅读源文件和相邻测试。
2. 列出该批次公开运行时函数。
3. 为每个函数判断测试缺口。
4. 编写或补充测试。
5. 运行相关测试。
6. 必要时在汇报中说明源码 JSDoc/TSDoc 缺口。
7. 如果遇到语义不清、注释冲突、实现疑似 bug，在批次汇报中列出，等待使用者或更强模型判断。
8. 最后运行必要验证命令。

## 写测试时的语言规则

- 当前规范是“中文负责描述，英文负责结构”。
- 历史文件中的英文注释、英文测试描述、英文日志不能自动视为新规范。
- 测试描述使用简体中文。
- 注释使用简体中文，并检查表达是否清楚、自然、优雅。
- 测试日志、调试说明、错误说明优先使用简体中文。
- 文档使用简体中文。
- 代码标识符使用英文。
- 约定俗成的代码词汇保持英文，例如 `mapper`、`predicate`、`options`。

详细规则见 [how-to-write-test.md](../guides/how-to-write-test.md)。

## 批次节奏硬约束

执行模型不能一口气修改大量内容。

如果本文档和 [`batch-execution-protocol.md`](./batch-execution-protocol.md) 有任何不一致，以批次执行协议为准。

单批次上限：

- 最多 1 个源码文件；或
- 最多 5 个强相关公开函数；或
- 最多 20 个新增/修改测试用例。

达到任一上限后必须停止当前批次。

每个批次结束后必须：

1. 运行相关测试。
2. 必要时运行 `bun run type-check`。
3. 必要时说明是否发现源码 JSDoc/TSDoc 缺口。
4. 总结本批次完成项、验证结果、遗留问题。
5. 等使用者明确要求“继续”后再开始下一批。

不要自动连续执行多个批次。即使还有明显剩余工作，也要先停下来汇报。

## reference 说明规则

默认不新增额外 reference 文档，也不要为了套格式强行写说明文件。

函数说明优先写在源码 JSDoc/TSDoc 中。如果需要统计哪些说明待补，统一写入 `docs/jsdocs.md` 总表。

执行模型不要自行创建说明文档。如果觉得 JSDoc/TSDoc 不够承载，应在汇报中提出，由使用者决定。

不要为了让描述更漂亮而省略不确定点。

## 遇到不确定时怎么做

执行模型不要自行做高风险判断。

如果出现以下情况，停止修改相关函数的源码语义，只记录问题：

- 源码注释和实现不一致。
- 现有测试和函数实现不一致。
- 函数名表达的语义和实际行为不一致。
- 需要决定是否改变公开 API。
- 需要决定是否保留 bug 作为兼容行为。
- 类型定义与运行时行为冲突。
- 需要新增依赖或改变测试框架配置。

记录格式：

```md
## 函数名或文件名

- 源码：`src/...`
- 当前批次：
- 观察到的现象：
- 已写测试：
- 不确定点：
- 建议交给强模型判断的问题：
```

记录后继续处理同批次中不受影响的函数；如果整个文件都受阻，就结束当前批次。

## 允许修改的内容

当前阶段允许：

- 新增或补充 `*.test.ts`。
- 使用者明确要求时，更新 `docs/jsdocs.md`。
- 更新计划文档中的执行状态。
- 为了让测试可读，少量调整测试辅助代码。

当前阶段默认不做：

- 不重构源码。
- 不重命名公开函数。
- 不大规模改 `reference.md`。
- 不改构建配置。
- 不引入新依赖。

如果测试暴露 bug，先写清楚当前行为和期望行为，不直接修源码，除非用户明确要求。

## 注释处理规则

执行测试补齐时可以顺手处理同批次内明显不合当前规范的注释。

允许：

- 把同批次附近的英文说明性注释改成清楚的简体中文。
- 删除明显重复、无信息量或已经过时的注释。
- 将生硬直译的注释改成自然的中文描述。

不允许：

- 大范围重写无关文件注释。
- 为了改注释而扩大当前批次范围。
- 修改源码行为来匹配注释，除非用户明确要求。

如果注释和实现冲突，在批次汇报中列出，不要自行决定哪一个代表真实语义。

## 验证命令

每个批次完成后运行最小必要命令。

推荐顺序：

```bash
bun test <相关测试文件>
bun run type-check
```

阶段性完成后运行：

```bash
bun test
bun run build
```

如果命令失败：

- 先判断是否是本批次改动导致。
- 能直接修测试就修测试。
- 涉及源码语义时，记录到 unresolved 文档。

## 批次交付格式

每个批次完成后，总结：

```md
完成：
- 新增/补充了哪些测试。
- 是否发现了源码 JSDoc/TSDoc 缺口。

验证：
- 运行了哪些命令。
- 结果如何。

遗留：
- 有哪些需要使用者或更强模型判断的问题。
```
